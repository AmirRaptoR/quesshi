Quesshi · refactor review record

Refactor decisions

Quesshi keeps .NET, Orleans and Blazor and becomes a multi-tenant platform that grows by plugins, on PostgreSQL only. This is what was decided and what three review rounds with Codex, against the real source code, changed. Nothing is built yet.

Decisions

Marked ones shape everything else. Open any line for the detail.

The plan

Key · awaiting your confirmationThe platform is built as a second solution beside today's code, and production moves once.Today's app keeps running and getting fixes, untouched, until the new one is complete.
  • A separate solution under platform/ with its own host, Blazor client, tests and CI job. The two never run in one process.
  • Kept code is copied into it with its tests, not moved, because today's projects still use it.
  • Fixes made to today's version meanwhile are tracked in a parity list and checked against the latest production commit before the cut-over.
  • Each milestone is deployed to a staging host as its own tenant.
  • The old tree is deleted in the cut-over release.
Eight milestones, each with a stated "done".The riskiest measurement comes second, not last.
  • 1. Foundation: database roles, migrations, tenants, jobs and events, new host and shell.
  • 2. The live-path prototype and its benchmark, which fixes the player limit or the need for batching.
  • 3. Identity. 4. Content and the five existing question kinds.
  • 5. The engine and the three existing formats. 6. Feature plugins.
  • 7. Flashcards, required before the cut-over. 8. Cut-over, with a rehearsed roll-back.
Rolling back means switching to a complete, untouched copy of the old deployment.Kept for an agreed window and rehearsed on staging first.

That copy is the image, the compose file, its configuration and keys, the MongoDB and Redis volumes, and a snapshot of the media folder. What was played on the new platform in between is lost.

What stays and what goes

Kept: the rules, and most of what surrounds the game.Scoring, the question-set builder, live standings, voting results, the map, mail, the admin panel's functions, translations, CSS.
  • Their existing tests move with them and become the proof that the new formats play like today.
  • Adapted, not kept as is: the sort shuffle, the import pipeline, the prompt builder, the sign-in code check, the deployment scripts.
KeyReplaced: the three parallel game stacks, the storage, the realtime channel.Three aggregates, three grains, three APIs and two SignalR hubs become one engine, one grain type, one API and one stream.
  • MongoDB and Redis go; PostgreSQL holds everything, including Orleans' cluster membership.
  • Six other grains go: player, two matchmaking, two settings, the question generator.
  • The Player document splits into accounts, players and plugin tables.
  • Database-per-tenant and the ambient "current tenant" go; the default tenant quesshi is no longer special.

Orleans and the session engine

KeyOne grain type for every format; grains write, the database is read.The grain is a session's only writer. Views, lists and history never wake a grain.
  • Its key carries the tenant, passed explicitly to every database call.
  • Orleans grain storage and reminders are not used. Nothing is stored as a blob.
  • Today, listing a player's matches wakes one grain per match.
Every write is guarded by the session's version.So two activations of one grain, which Orleans allows briefly after a failure, cannot both write.
  • The first statement of each transaction updates the session only if its version is the one the grain last saw.
  • No row updated means another activation wrote: this one drops everything and deactivates.
  • A lost connection during commit is treated the same way. The client retries, and position checks make the retry safe.
Creating a session is a database insert, not a grain call.That lets matchmaking pair two players and start their game in one transaction.
  • Three shapes: a lobby; a started session with its roster; an open session its creator can play before anyone joins, which is today's async challenge.
  • The caller supplies the id, so a retried create cannot make a second session.
Deadlines live in one column; a once-a-second sweep wakes sleeping sessions.A grain timer handles the next two minutes; the sweep covers restarts and 48-hour forfeits.
  • The sweep never writes to a session.
  • A format bug counts as a fault and ends the session after five tries. A database outage never does.
  • The core can end any session without calling its format: cancelled by owner or admin, expired, fault, outage.
The one P0 of the earlier design still applies: a format declares whose position counts.The session's for live and poll; each player's for async duel and flashcards.

The engine uses that single position to reject stale commands, detect duplicates and build the response.

Today's rules, kept exactly

Key · changed by reviewReview caught my design drifting from the real game in about twenty places.Each is now restored from the source, with the existing tests as the specification.
  • Live: one countdown, 2-second grace, 40-second outage limit, today's reveal timing, today's standings where finishers outrank everyone who left.
  • Async: forfeit 48 hours after creation; the creator can play before an opponent arrives.
  • Poll: answers can be changed until the slot closes; "not applicable" and the roster's special answers; results shown only at the end.
  • Lobbies: the owner leaving cancels it; invitations only to friends or recent co-players, never guests; rematch only for live.
  • Content: exactly four options; category allow-lists per family; at most three chosen categories; the draw's fallbacks.
  • Friends are mutual. Reports only for questions from your own recent games. Guests denied by default.
  • A penalty takes a score to zero and no further; the rest is forgiven.
Eleven deliberate changes are listed in one table.If it is not in that table, it should play as today.
  • Yours: one account across tenants.
  • From the design: cookie sign-in; boards and stats a second or two behind the result; guest-started runs never ranked; per-format and weekly or monthly boards; answers stored as rows; media stored as files; languages as codes; flashcards.
  • Quirks fixed: quitting a live game others finish now costs a penalty; accuracy no longer counts rounds after you left; a tied async game no longer gives everyone a draw; the penalty formula no longer wraps around at very large counts.

Plugins, tenancy, identity

Five plugin types around a fixed core, enforced by project references.Kinds, formats, features, sign-in methods, content sources.
  • Formats reference a contracts project that contains no database interface, so a format cannot touch storage.
  • Features see the core only through an interface project; the core's own types are internal.
  • Features do not own grains.
  • Each extension point is built only when its first real user is.
KeyA game result never waits for a feature.Stats and boards follow by events, each applied exactly once.
  • This replaces today's settlement through the player grain, with its checkpoints, dedup list and retry reminder.
  • The leaderboard keeps a ledger and folds it in time order, so results processed late still come out right.
  • Deleting a player's data is mandatory for every plugin and cannot be switched off.
One schema for all tenants, row-level security, three database roles.No running credential can read two tenants in one query.
  • Tenants, hosts and what each has switched on move from appsettings.json into the database.
  • "Enabled" means offered for new play; games already running keep going.
One account across tenants; cookie sessions replace the two JWT schemes.Sessions can now be revoked, which deletion and bans need.
  • Antiforgery token on every changing request, including uploads.
  • Upgrading a guest to an email that already has a profile here is refused, as today.
  • The last owner of a tenant and the last platform admin cannot be removed, checked under a shared lock.

Delivery and the Blazor client

KeyOne app-wide stream of server-sent events; commands by POST.It replaces both hubs, the three notifier interfaces and the client's fourteen events.
  • The server pushes each player's whole current view. A reconnect just gets the current state.
  • A 2-second reconcile repairs anything a lost notification missed.
  • In Blazor it is a streamed HttpClient request, not the browser's EventSource.
The first visit by invite link is treated as the path that matters.A plain server page appears at once; the app loads behind it and takes over.
  • The admin area and the map are lazy-loaded assemblies.
  • The service worker stops downloading everything at install.
  • The shell stays a static, integrity-checked file; theme and configuration come from three small per-tenant routes.
  • Target on a mid-range phone on mobile data: invite page usable in under a second, app playable in under four.
Fetching a media URL someone typed is fenced.Today the browser loads such URLs; now the server would, so internal addresses are refused.

Only http and https, the resolved address is checked and used, redirects are limited and re-checked, and size is capped.
