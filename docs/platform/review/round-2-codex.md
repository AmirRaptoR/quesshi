1. **P0 — §§7.3, 8.2; `sessions` constraint on `started_at`.** An async lobby must now finish as `forfeit` 48 hours after creation even if nobody started it, but the schema rejects every `finished` row whose `started_at` is null. That transition will roll back instead of releasing the lobby and recording its result. **Fix:** allow an unstarted async session to finish by forfeiture, with an explicit constraint exception; do not fabricate a start timestamp.

2. **P0 — §7.4, four-outcomes table — R1 #5–7 partially resolved.** “Stale activation” is grouped with rollbacks for which “the current state is still right,” although a zero-row fencing update proves that another activation changed the database. The stale activation can consequently keep returning obsolete views and rejecting every subsequent write, contradicting §18’s requirement that it deactivate. **Fix:** give `StaleActivation` its own outcome: discard the entire cache, dispose its timer, call `DeactivateOnIdle()`, and finish the turn with a retryable error.

3. **P1 — §§7.4–7.5: retry updates reintroduce writers outside the grain.** The sweep may now push `retry_at`, including after a stale activation or unknown commit; an unfenced update can put a successfully advanced session into backoff, while a version-bumping update invalidates the live grain’s cache. This contradicts both the single-writer rule and the four-outcomes protocol. **Fix:** keep delivery failures as sweep-local backoff; persist session retry state only through a fenced grain transition, adopting the resulting version or deactivating after an ambiguous write.

4. **P1 — §7.5; `due_sessions()` — R1 #9 is not fully resolved.** “Every failure moves `retry_at`” cannot hold when PostgreSQL is unavailable, and a five-second Orleans call timeout does not prove the callee stopped running. Once the caller stops waiting, the same earliest rows can be selected and dispatched repeatedly, still hiding later overdue sessions behind the SQL limit. **Fix:** add discovery pagination or exclusions for locally backed-off IDs and retain bounded outstanding-call bookkeeping independently of caller timeout; cancellation is cooperative, not termination. [Orleans cancellation documentation](https://learn.microsoft.com/dotnet/orleans/grains/cancellation-tokens).

5. **P1 — §13; `leaderboard_entries`: abandonment occurrences lack a canonical identity across projections.** Points produce six ledger entries per session, but penalties are described as “one entry” without specifying its board/period projections; counting copied penalty entries can turn one abandonment into several occurrences, while recording only one leaves other boards unpenalized. Restricting the count to the current month/week also incorrectly resets the rolling seven-day tier at a period boundary. **Fix:** record each abandonment once per tenant/player/session, including the zero-cost first occurrence; compute its tier across periods from distinct abandonment events, then project that one amount onto explicitly defined boards and periods.

6. **P1 — §13; `player_stats.points`, `leaderboard_scores.score` — R1 #30–31 remain partly unresolved.** The stats plugin sums earned points, while the leaderboard independently subtracts penalties, so the profile’s points and its all-time leaderboard score diverge after an abandonment. Today both come from `Player.Stats.TotalScore` (`src/Quesshi.Grains/PlayerGrain.cs:49`, `:54`, `:64`; `src/Quesshi.Web/Pages/Profile.razor:29`). **Fix:** define the existing profile total as the canonical all-time net score, obtained through the leaderboard’s read-only query; name gross earned points separately and define the display when that feature is disabled.

7. **P1 — §§7.4, 8.1–8.2, 9.4; `session_answers.revision` — R1 #21 is not fully resolved.** The generic duplicate rule still returns immediately when an answer row exists, activation loads only *which* seats answered, and the HTTP command shape omits `revision`; together these prevent or misclassify legitimate poll replacements. A reconnect or second tab also needs the authoritative revision to avoid resending a different selection with an already-used number. **Fix:** carry revision through HTTP, Orleans, cache and the caller’s view; define replacement as an update to the same answer row only for a higher revision while the slot remains open, without incrementing the answered count, and define equal-revision/different-payload conflicts.

8. **P1 — §§7.3, 13: pairing does not specify automatic start or complete initial construction.** The protocol deletes both queue entries and creates/seats a session, but ordinary creation produces a lobby; today both random-pairing paths explicitly start the duel (`src/Quesshi.Server/Api/GameEndpoints.cs:178`, `src/Quesshi.Grains/LiveMatchmakingGrain.cs:300`). Calling the grain before commit cannot read the inserted session, while calling it afterward can fail after the entries are gone. **Fix:** give transactional creation an explicit paired-start mode that constructs the complete roster, draws snapshots and applies `Start` before commit; otherwise persist a durable start obligation in that same transaction.

9. **P1 — §§7.3, 13: async matchmaking still changes the waiting challenge’s lifecycle — R1 #50 partially resolved.** Today enqueueing creates and returns an actual challenge, its code and fixed question set; matching later uses that same challenge (`src/Quesshi.Server/Api/GameEndpoints.cs:206`, `:208`, `:211`). Creating the session only when pairing occurs resets its 48-hour clock, draws different questions and removes the pre-existing challenge/link. **Fix:** store the waiting async session’s ID in the entry and pair into that session with a fenced transactional claim that respects existing grain writes; alternatively list delayed session creation and its changed clock/link behaviour explicitly in §19.4.

10. **P1 — §13: pairing revalidation omits expiry and deleted players.** An async entry just beyond 48 hours can be paired before the cleanup job runs, and a tombstoned player can still have an entry while its plugin cleanup is pending; step 3 checks only matching settings, bans and presence. **Fix:** recheck expiry and `players.deleted_at` under the player locks before deleting entries or creating the session, and skip/prune invalid candidates rather than repeatedly selecting the same unusable head entry.

11. **P1 — §§4, 19.2: “beside” has no executable project/host boundary.** Most listed project names already exist, and the old host already owns `/api/auth`, `/api/me`, `/api/admin`, the Blazor fallback, default bearer authentication and global Orleans configuration (`src/Quesshi.Server/Program.cs:36`, `:45`, `:248`, `:256`, `:264`). Registering the new platform beside these without isolation creates duplicate routes, authentication/DI collisions and conflicting membership registrations. **Fix:** specify separate staging host/client projects with distinct assembly names and new-only registrations; if one host is required, spell out route prefixes, authentication schemes, keyed services, one membership provider, retained named Redis storage/reminders and scoping of the legacy grain filter.

12. **P1 — §19.2: milestone dependencies and “played for real” remain inconsistent.** Milestone 2 needs session/seat tables that arrive in milestone 5, milestone 4 promises report screens before the reports plugin in milestone 6, and identity/content screens need a client shell whose construction is not assigned until session work. Milestones 1–4 cannot satisfy the stated playable staging exit condition. **Fix:** assign the minimal host/config/auth shell to foundation/identity, bring the real persistence subset into the prototype, move report behaviour with its plugin, and define milestone-specific exits—health checks, benchmark, sign-in, authoring, then end-to-end play.

13. **P1 — §§11.2–11.3, 15–16: antiforgery has no bootstrap or identity-change protocol.** A cached static shell contains no request token, and a token issued anonymously or as a guest can become invalid after sign-in or upgrade; both player and admin cookies also accompany same-origin requests, so the token must bind to the route’s selected identity. Merely adding antiforgery middleware does not specify validation of every JSON command. **Fix:** add a non-cacheable same-origin token endpoint, obtain fresh tokens after every authentication change, select the appropriate authentication scheme explicitly, and apply a core validation convention to JSON and multipart writes. [ASP.NET Core antiforgery documentation](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery).

14. **P1 — §§5.2, 16: string descriptors do not establish trimming roots — R1 #35/#54 partially resolved.** Removing eager `typeof` references solves lazy loading but can remove the linker’s evidence that component constructors and parameter members are needed; source-generated JSON preserves payload metadata, not dynamically resolved Razor components. A successful assembly download can therefore still leave an unresolvable or unusable component. **Fix:** give each lazy assembly a rooted registration entry point or explicit linker annotations/descriptors preserving its components and parameters, and exercise every registered component in the published-build test. [Trimming guidance](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/fixing-warnings).

15. **P1 — §12: fetching arbitrary media URLs creates a new server-side request capability.** Previously a supplied URL was rendered by the browser; now a tenant author/editor can make the server fetch loopback, private-network or cloud-metadata endpoints, including through redirects. The existing Wikipedia provider starts from controlled Wikipedia responses and is not a general URL-fetch authorization policy. **Fix:** define an HTTP/HTTPS fetch policy that rejects internal destinations and validates redirects/DNS resolution, limits bytes while streaming, and treats existing relative media paths as authorized tenant assets rather than arbitrary server URLs.

16. **P1 — §§7.5, 8.2, 19.4: restored live constants still do not restore today’s timing — R1 #25/#42 partially resolved.** Today a timeout closes at the scheduled question boundary and the reveal ends three seconds after that boundary (`src/Quesshi.Domain/LiveMatch.cs:545`, `:619`); after two seconds of grace, approximately one second of that reveal remains. The new rule starts a full three-second reveal at actual closure and opens delayed questions from actual time, changing pacing even during normal timeout rounds. **Fix:** preserve the existing scheduled anchors, or explicitly list actual-opening anchors, longer timeout reveals and changed catch-up behaviour in §19.4; do not describe the timing as unchanged.

17. **P1 — §§8.2, 13, 19.4: stats parity still differs at important boundaries.** Today async settlement skips seats whose run never existed (`src/Quesshi.Grains/MatchGrain.cs:387`), whereas the target counts every player seat, so untouched forfeits can manufacture played games and wins/draws; voting also currently performs no player-stat settlement. Separately, voting’s served counter is updated per opened slot, but the target’s only question aggregate excludes all ungraded questions (`VotingMatchGrain.cs:354`). **Fix:** retain an explicit “run began” fact for async stats and preserve the voting usage counter; list any decision to add poll played counts or alter accuracy/served-count semantics in §19.4.

18. **P1 — §9.3: the new 64 KB frame cap has no corresponding content/view bounds.** Current question validation permits prompts and option text large enough for one card to exceed that cap, and terminal views can also contain substantial answer history. An approved question can therefore become unplayable through repeated oversized-frame failure. **Fix:** validate the serialized card/reveal size before approval and draw, and move large history/results to bounded paged responses or define a framing protocol that preserves the complete view.

19. **P1 — §§7.3, 11.3, 13: invitations and rematches still lack today’s authorization rules.** Refusing guests is insufficient: today invitations require a friend or recent co-participant and refuse guest targets (`src/Quesshi.Server/Live/LobbyHub.cs:201`, `:204`, `:238`). Rematches preserve the original owner, clamp capacity to the current limit and notify/invite other participants (`src/Quesshi.Grains/LiveMatchGrain.cs:464`, `:488`), none of which is specified by “same settings” plus uniqueness. **Fix:** state and implement those checks and construction rules, including the fallback when friends are disabled; also explicitly identify any new rematch support for formats that lack it today.

20. **P1 — §11.2: the new last-owner/platform-admin guards need shared serialization.** With two active tenant owners, concurrent requests can each observe the other and remove both; locking each affected admin independently does not protect the tenant-wide invariant. The same race applies to the last active platform administrator. **Fix:** serialize owner-membership changes under a common tenant lock and platform-admin changes under a common global lock, then recheck counts and revoke sessions in the protected transaction.

21. **P2 — §§13, 19.4: the ledger’s exact reconciliation is a deliberate behaviour change, not merely a storage change.** Current penalties are dated at match end and explicitly may undercharge late settlements without retroactively raising earlier tiers (`src/Quesshi.Grains/LiveMatchSettlement.cs:85`, `src/Quesshi.Domain/Player.cs:128`); the target dates them at departure and recomputes later penalties. For example, a departure and session end on opposite sides of a week boundary change the affected period and potentially the seven-day tier. **Fix:** list event-time ordering, departure timestamps and retroactive tier correction in §19.4, and specify the window boundary and equal-time ordering; keep the improved protocol if that change is intended.

22. **P2 — §§7.4, 19.2: the prototype’s stubs can under-measure the claimed path.** A stub format/stream may omit snapshot loading, grading, production-size serialization and final-round event writes, yet its result is supposed to fix capacity before those components exist. Passing that benchmark would not establish the advertised complete-turn budgets. **Fix:** define the representative fixture and required real components now, include cold activation and pool contention, and repeat the same gate with production kinds, renderer and enabled ending handlers before cut-over.

23. **P2 — §19.2: moving “kept” code can break the still-present old projects, and the long branch can miss production fixes.** For example, moving `QuestionSetBuilder` out of Application or replacing `Language` while legacy grains still reference them makes the solution uncompilable; deleting a replacement’s old implementation also prevents straightforward incorporation of a later production fix. **Fix:** retain or extract a genuinely compatible shared implementation until legacy consumers are removed, maintain an explicit parity checklist for production fixes, and require final verification against the latest production commit rather than the branch’s starting revision.

24. **P2 — §7.3: creation retries and first activation are not defined.** If creation commits but its HTTP response is lost, retrying with a newly generated ID creates another lobby; if a grain is called before the creating transaction commits, it can load “not found” and remain activated with that absence. “No grain exists yet” is not a runtime guarantee. **Fix:** give creation a stable request identity, publish/call the grain only after commit, and deactivate rather than retain a negative activation cache; specify the complete initial `due_at`, roster, state and snapshots for running solo sessions.

25. **P2 — §4: `Plugin.Api` exposes impure capabilities to the pure formats.** Moving contracts out of Application enforces core visibility, but formats can still reference `ITenantDb`, `ITenantTx`, `ISessions` and content services from their allowed API assembly; banning Npgsql/network types does not necessarily ban calls through those interfaces. **Fix:** separate pure contract namespaces and reject compiled Format dependencies on the impure API surface, including constructor parameters; place cross-feature query result records in neutral contracts rather than another feature’s namespace.

26. **P2 — §§11.3, 17: framework antiforgery introduces a missing key-persistence dependency.** If the implementation uses ASP.NET Core antiforgery, different silos or replacement containers without a shared persistent Data Protection key ring cannot validate one another’s tokens, producing intermittent 400 responses or invalidating every open tab on restart. `SECRET_KEY` for code HMACs does not automatically configure that ring. **Fix:** specify persistent/shared Data Protection storage and application identity, or explicitly select a different token implementation with its own verification protocol. [Antiforgery’s Data Protection dependency](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery).

27. **P2 — §§10.4, 16: theme/config refresh and offline first paint have no coherent cache policy.** The shell now fetches `/theme.css`, but a pushed config change only triggers configuration rereading; an unchanged CSS URL can keep the old branding, and an offline cached shell has no specified last-known theme/direction bootstrap. §10.4 still says the server writes tokens into the shell, contradicting §16. **Fix:** define versioned or revalidated theme/manifest responses, reload them on relevant configuration changes, and cache a non-sensitive tenant bootstrap for offline shell rendering; make the preview and initial shell use the same language/direction rules.

28. **P2 — §§9.1, 9.5–9.6: page-owned streaming can remove the application-wide inbox and presence channel.** The stream is now cancelled with its page, but invitations and matchmaking results must arrive on Home/Profile as well as a session page; live queue eligibility itself depends on an open stream. An implementation that opens streams only for `session={id}` makes waiting players appear offline. **Fix:** define a shell-owned stream that supports no watched session, or explicitly require replacement streams on every authenticated page while preserving inbox and presence continuity.

29. **P2 — §§7.1, 11.1, 19.4: guest upgrade has two additional unlisted changes.** Today upgrading to an already-used email returns `AddressTaken` (`src/Quesshi.Application/UseCases/AuthService.cs:74`), whereas the target switches to the existing profile and abandons the guest; also, eligibility is fixed when taking a seat, not when the “run started,” so upgrading in the lobby still leaves the later run unranked. **Fix:** list the existing-profile switch and describe the eligibility boundary accurately in §19.4, or move the eligibility snapshot to run start if that is the intended rule.

30. **P2 — §§6.6, 8.2: the poll-roster answer contract still differs from the current accepted contract.** `VotingMatch.ValidateAnswer` accepts `NotApplicable` without restricting the answer source (`src/Quesshi.Domain/VotingMatch.cs:270`), and existing roster tests submit it, while the target lists only a seat, several or none. **Fix:** preserve it as an accepted abstention with the existing result treatment, or explicitly list removal of that accepted answer as a contract tightening; the existing tests cannot be called the unchanged specification otherwise.

31. **P2 — §§7.4, 9.2–9.3; `plugin_effects`: the fourth version has no defined source.** Session, inbox and configuration versions have persisted counters, but effects have only markers/timestamps; pending-to-failed changes occur in `jobs`, and failed-to-pending can occur on rerun without adding a marker. Equal or invented effects versions can allow an old pending response to overwrite a failed/done response. **Fix:** define an effects revision or generation protocol covering handler completion, dead jobs and reruns, and specify its reconnect behaviour independently of session version.

32. **P2 — §§10.4, 19.1: some “kept” generation/auth code needs substantial adaptation for the new contracts.** `QuestionPromptBuilder` maps unknown languages to English and reads `Category.NameEn` (`src/Quesshi.Infrastructure/Generation/QuestionPromptBuilder.cs:88`, `:291`), so passing a newly enabled language through it silently generates English content. Likewise, the current OTP service performs separate get/save/delete operations rather than the new atomic verification protocol. **Fix:** classify these components as adapted, define language-name/category-name resolution and translation availability, and replace the OTP orchestration rather than merely its storage adapter.

33. **P2 — §§7.3, 8.1; `session_participants.exclusive`: defer the unused exclusivity path.** None of the four initial formats uses it, yet the core still carries a format switch, seat flag, partial unique index and clearing obligations across every lifecycle path. This adds states and tests to the refactor without preserving any current behaviour. **Fix:** defer that field/index/API path until a concrete exclusive format is implemented; keep today’s multi-lobby rule.

34. **P2 — §19.2, milestone 7: flashcards cannot be optional after cut-over under the stated release decision.** The sentence allowing milestone 7 to move after cut-over contradicts §20’s requirement that all four formats ship in the first release. It also weakens the stated use of solo, ungraded play to validate the engine contract. **Fix:** remove that option and keep flashcards in the cut-over acceptance checklist.

35. **P2 — §§17, 19.2: keeping Mongo/Redis volumes alone does not make rollback operational.** The old image also needs its old Compose services, connection settings, JWT configuration and original uploaded/sourced media; the new pipeline removes or replaces several of these (`deploy/deploy.sh:62`, `compose.yaml:14`). Redeploying the image against retained volumes can therefore fail startup or restore games with broken media. **Fix:** retain and rehearse the complete previous deployment configuration and media snapshot alongside the image and database volumes, and prevent new cleanup from touching those rollback assets during the window.

36. **P3 — §19.4: two entries misdescribe what changes.** Core results are committed immediately, not recorded later “by events,” and today’s full answer snapshots are already retained indefinitely—the source expressly says finished grain state is never cleared (`src/Quesshi.Domain/Match.cs:368`; `LiveMatch.cs:465`). **Fix:** describe immediate core settlement followed by asynchronous feature effects, and describe answer-history changes as relational persistence/readability rather than a new retention policy.
