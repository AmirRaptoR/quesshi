1. **P0 — §19.2, stage 1: removing Redis leaves existing reminders and storage users unsupported.** The bridge covers “the three existing grains,” but matchmaking and settings grains also use `PersistentState`; game creation, settlement recovery, voting expiry and nightly generation still register reminders (`src/Quesshi.Grains/MatchGrain.cs:88`, `LiveMatchGrain.cs:130`, `VotingMatchGrain.cs:122`, `QuestionGeneratorGrain.cs:22`). Stage 1 cannot run as written after removing the Redis providers. **Fix:** inventory every storage/reminder user and explicitly retain PostgreSQL-backed bridge providers until its replacement ships, or move those consumers to durable jobs/deadlines in stage 1.

2. **P0 — §§19.2–19.3: dropping bridge storage destroys history created after the initial cut-over.** Starting empty removes migration obligations for *today’s* players and history; it does not remove obligations for production sessions created during stages 1–3. Async/live answer history remains in grain snapshots, so deleting the bridge in stage 4 strands those sessions and loses their detailed history. **Fix:** design conversion of bridge snapshots into session/items/answers/results before deleting each old stack, or retain a read-only legacy history reader and drain active sessions first.

3. **P0 — §§7.4, 13: matchmaking’s atomic session creation has no compatible transaction boundary.** Pairing promises to create a session and delete both queue entries in one transaction, while the session grain is declared its only writer and feature code receives no grain factory or connection. Calling a session grain that opens its own transaction cannot fulfil that promise: a crash can leave a created session with queue entries still available for pairing. **Fix:** specify a core `CreateInTransaction` operation that inserts a fully initialized session, seats and inbox changes using the queue’s existing transaction; activate the session grain only after commit, with an explicit exception to “only writer” for initial creation.

4. **P1 — §13; `matchmaking_entries`: the queue lacks the session grain’s stale-writer protection.** Two queue activations can hold the same entries; both can create matches unless pairing conditionally consumes the authoritative entries and verifies that both were consumed. The offline-cleanup job is also a second writer, so an activation can retain an entry the job deleted. **Fix:** lock and revalidate both entries in a deterministic order, require exactly two successful conditional deletions in the creation transaction, and reload/invalidate queue memory after failed or ambiguous commits; route pruning through the queue or make it obey the same database protocol.

5. **P1 — §7.4, step 5; `sessions.version`: the fencing statement needs an executable protocol.** PostgreSQL treats an update affecting zero rows as success, so merely including `where version = @expected` does not roll back earlier answer, seat or job writes. Two activations can therefore commit conflicting effects if the implementation misses that distinction. **Fix:** perform a tenant-and-session-scoped conditional update with `RETURNING`, require exactly one row before committing any effects, and throw a specific concurrency exception otherwise; state that every session mutation participates in that transaction.

6. **P1 — §7.4, steps 6–7: committed work and post-commit failures are conflated.** A commit can succeed while its response is lost; rendering the caller’s view or arming the next timer can also throw after a confirmed commit. Treating all these cases as a failed transition, retrying mutations, or recording a format fault can duplicate work or misclassify a healthy session. **Fix:** distinguish definite rollback, unknown commit outcome, confirmed commit and post-commit delivery failure; invalidate memory and request deactivation on an unknown outcome, never rerun its mutation from the old copy, and let retries inspect durable position/answer markers.

7. **P1 — §§7.4, 7.5: activation loading and copying are underspecified for correctness.** Loading session, seats and counters through separate snapshots can produce a working copy that never existed, while a shallow copy of mutable seat state, sets or JSON-backed structures can mutate the authoritative cache before a failed transaction. **Fix:** load the activation through one consistent read transaction and define an isolated copy or immutable transition result covering every mutable field; test failure after modifying nested state.

8. **P1 — §§7.4, 8.1: activation contents do not support the synchronous grading contract.** Activation loads “item metadata,” but `s.Grade(command)` synchronously needs the stored payload/resolved value and duplicate-answer information; those are not metadata. Fetching them during `Apply` would violate the synchronous contract, while reconstructing them risks grading against a different arrangement. **Fix:** specify which snapshots and answer keys are cached, and which are asynchronously loaded by the engine before invoking the format; include that work in the answer latency measurement.

9. **P1 — §7.5; `due_sessions()`: bounded discovery can starve unrelated sessions.** Every silo asks for the same earliest bounded batch; a hung grain call or database failure can keep that batch overdue, repeatedly occupying discovery while later sessions never appear. “Never overlaps itself” makes a sweep especially vulnerable if it awaits an entire stalled batch. **Fix:** define bounded concurrent dispatch, per-call timeouts, local outstanding-call deduplication and fair discovery beyond the oldest blocked rows; demonstrate progress with several permanently unresponsive entries.

10. **P1 — §7.5: timeout faults must be separated from infrastructure failures.** Counting connection failures, cancellation, concurrency rejection or an unknown commit as a format fault can cancel healthy games after five attempts; refusing to count them without bounding retries can instead hammer an unavailable database. **Fix:** count only deterministic format/transition failures after a known rollback, fence the failure-record transaction, and give infrastructure failures a separate retry policy that does not award misses or trigger `fault`.

11. **P1 — §§7.4, 19.2: the 500-player feasibility gate comes after too much dependent work.** At the advertised 2 ms per answer, 500 serialized transactions occupy approximately one second—the entire interval from 250 ms before the deadline through 750 ms after it, before activation, scheduling, pool waits and closing work. Non-reentrancy means awaits do not allow another answer or timeout to proceed, and adding silos does not increase one session’s throughput. **Fix:** move a representative PostgreSQL/Orleans prototype and burst benchmark before committing to the engine design; measure the complete occupied turn and decide batching, capacity or grace before implementing dependent screens and formats.

12. **P1 — §19.2, stage 1: existing repository ports cannot simply expose the target schema.** `Player` still contains email, friends, aggregate stats, per-category accuracy and settlement markers, while those facts move into global identity and plugin tables; voting also has its own repository, generation log and archived-state shape. Implementing the listed ports against only the proposed tenant/identity/content foundation leaves required fields and operations without storage. **Fix:** enumerate a temporary schema and mapping for every existing port, including voting, content settings, spend/generation logs and player settlement state, and name when each temporary structure is converted or removed.

13. **P1 — §19.2, stage 2: accounts cannot be introduced without converting stage-one production profiles.** Players created after stage 1 will already have email-based identities, guests, cached `PlayerGrain` objects and JWT sign-ins; stage 2 changes their keys and ownership relationships while they may have active sessions. **Fix:** include an idempotent conversion preserving player IDs, account-email deduplication, guest handling, cache invalidation and the JWT-to-cookie cut-over; the original “no carry-over” decision does not authorize another reset.

14. **P1 — §19.2, stage 3: “the three grains … otherwise unchanged” is not a workable compatibility boundary.** Their state and views still use `Question`, enum languages, integer choice indexes, boolean correctness and mode-specific snapshots (`src/Quesshi.Grains/SubmittedAnswer.cs:56`, `VotingMatchGrain.cs:220`, `src/Quesshi.Domain/LiveMatch.cs:381`). Generic records, variable choice counts and roster-answer unions cannot pass through those signatures unchanged. **Fix:** define explicit adapters and versioned bridge DTO/snapshot shapes for the existing three kinds and voting, or defer the envelope cut-over to each format’s engine migration.

15. **P1 — §19.2, stage 4: formats do not have independent client stacks to delete.** `Home`, `Lobby`, `Join` and `Profile` share mode routing, authentication state, invitations and hub clients; `Lobby.razor:573` still chooses among all three old join paths. Removing these shared pieces when async arrives breaks live and voting before their replacements exist. **Fix:** retain shared routing/transport adapters during coexistence, define which format owns each route and link, and remove shared pages/services only after the last consumer migrates.

16. **P1 — §§5.5, 19.2: the temporary stats handler has no durable execution mechanism.** The engine commits a terminal result in stage 4, but events and the job runner arrive in stage 5; an inline call to `PlayerGrain` can fail after commit, and database-only reads will no longer wake the finished session to resume settlement. **Fix:** bring durable job enqueueing and retry into the first engine stage, with a temporary handler using the existing per-match deduplication; define how its completed effects seed the later plugin markers and aggregates without double-counting.

17. **P1 — §§17, 19.1–19.2: the deployment pipeline is not reusable unchanged.** `deploy/deploy.sh:62` requires JWT secrets, lines 65–69 require Mongo/Redis volumes, and deployment switches only the app with `--no-deps`; CI provisions Mongo rather than PostgreSQL. The stage-one release will fail preflight or start without its new database, and automatic rollback can restore an incompatible Mongo-era image after PostgreSQL has accepted writes. **Fix:** include PostgreSQL provisioning, role/extension bootstrap, migrations, CI services, preflight and a concrete first-cut-over rollback policy in stage 1.

18. **P1 — §11.3: mandatory JSON content types break retained admin uploads and imports.** Existing media and import endpoints accept `IFormFile`, hence multipart requests (`src/Quesshi.Server/Api/AdminEndpoints.cs:176`, `:379`); they cannot satisfy a universal JSON-only unsafe-method rule. Keeping `.DisableAntiforgery()` from the JWT implementation would also be an unsafe cookie-era exception. **Fix:** permit bounded multipart requests on those specific routes with exact-origin validation and antiforgery protection, or explicitly redesign their upload protocol before stage 2.

19. **P1 — §§5.3, 11.1: guest permissions lose today’s deny-by-default rule.** A format’s `Guests` flag controls participation, but the design does not say whether guests may create sessions, invite, rematch, search/add friends, report, author content or edit their profile. Today guest access is explicitly allow-listed, including profile editing (`src/Quesshi.Server/Api/GameEndpoints.cs:27`, `:51`), while friend/search/report routes remain closed. **Fix:** define a core guest-operation matrix and apply it to core and feature route builders; preserve the existing exceptions unless a change is explicitly selected.

20. **P1 — §7.3: owner hand-over contradicts today’s lobby lifecycle.** An owner leaving currently cancels an async/live lobby, and voting’s owner leave calls `Cancel` (`src/Quesshi.Domain/Match.cs:207`, `LiveMatch.cs:240`, `VotingMatch.cs:105`). Hand-over allows remaining players to start a lobby its owner intended to close. **Fix:** preserve owner cancellation for the existing formats, or explicitly record this as a product change with its selection, authority and empty-lobby rules.

21. **P1 — §§6.6, 7.4: poll answers lose special options and answer replacement.** Today roster questions include “multiple participants” and “no participant,” fixed questions include “not applicable,” and a player may replace their answer until the barrier closes (`src/Quesshi.Domain/VotingMatch.cs:133`, `:238`). A roster “seat” or choice “index,” combined with “answer row already present means duplicate,” drops those options and locks the first answer. **Fix:** define discriminated poll answer records including the special values and specify replacement semantics with a command/revision token that distinguishes a retry from a new selection.

22. **P1 — §8.2: poll expiry changes both progress and outcome.** Today expiry is measured from the current slot’s served time; unanswered players become inactive, the barrier is reevaluated, and remaining players can continue; fewer than two active players produces no-contest (`src/Quesshi.Domain/VotingMatch.cs:171`). “Nobody answers for 48 hours → session completed” both changes the clock anchor and credits an incomplete session. **Fix:** preserve per-slot inactive-player removal and barrier reevaluation, and state the fewer-than-two rule and treatment of the unfinished final slot.

23. **P1 — §§8.1–8.2: poll result visibility and agreement calculations are undefined.** The current grain exposes other players’ answers and closed-slot results only after the match ends (`src/Quesshi.Grains/VotingMatchGrain.cs:418`); `VotingResults.cs:71` excludes not-applicable answers from pair comparisons and requires at least two comparable answers for slot agreement at line 124. Generic release rules and “results show agreement” do not preserve those privacy and denominator rules. **Fix:** specify the poll release point, counts, pairwise same/different totals, null percentages, rounding, all-agreed calculation and incomplete/no-contest result visibility using the existing fixtures.

24. **P1 — §8.2: async forfeiture changes its anchor and zero-answer result.** Current `Match.TryForfeit` uses `CreatedAt + 48 h` and builds standings even if nobody answered (`src/Quesshi.Domain/Match.cs:340`); the target starts a fresh 48-hour allowance at session start and makes zero-answer runs no-contest. A lobby started near its expiry can therefore last almost twice as long, and zero-answer games stop recording draws. **Fix:** state separate lobby/run deadlines and preserve the current anchor and outcome, or list both changes explicitly instead of calling the format “exactly” today’s behaviour.

25. **P1 — §§7.5, 8.2, 19.1: live timing is changed in three places.** Current live uses a single initial 3-second countdown (`src/Quesshi.Domain/LiveMatch.cs:192`), 2-second network grace (`MatchRules.cs:26`) and a stale threshold of 40 seconds (`LiveRules.cs:22`); the target describes countdown/question/reveal “repeated per slot,” 750 ms grace and a 10-second outage threshold. These alter pacing, accepted answers and cancellation outcomes despite the “constants kept” claim. **Fix:** preserve the constants and one initial countdown, or explicitly document the selected changes and adjust the benchmark and regression scenarios accordingly.

26. **P1 — §8.2: live standings omit the abandoner ranking and awarded-score rules.** Today finishers rank above every abandoner regardless of score; abandoners rank by elimination round, ties share a place, and their standing score is zero (`src/Quesshi.Domain/LiveMatch.cs:644`). “Ties share a place” alone permits a high-scoring quitter to outrank a survivor or receive banked leaderboard points. **Fix:** define those groups, ordering and outcomes, and distinguish displayed banked score from the score eligible for settlement.

27. **P1 — §§10.3, 12, 19.1: content settings lose family-specific category allowlists.** Today category eligibility is the intersection of active categories and a trivia/voting allowlist; player choices are capped at three, and no selection randomly chooses up to three (`src/Quesshi.Application/Ports/ContentSettings.cs:4`, `UseCases/CategorySelection.cs:8`). Replacing `ContentSettings` with unnamed capability settings does not say who enforces those rules, allowing a direct session request to draw disabled categories. **Fix:** name the bank/source settings and enforce the family allowlist, activity, supported language and three-category selection limit inside the authoritative draw path.

28. **P1 — §13: reports preserve suppression but drop authorization to report a question.** Today the report endpoint validates the reason and checks that the question belongs to the caller’s recent match history (`src/Quesshi.Server/Api/GameEndpoints.cs:523`). The target describes only lock/insert/count, so three accounts can suppress an arbitrary question they never encountered. **Fix:** specify the served/session-membership check and allowed reasons before insertion, retain one report per player/question, and explicitly decide whether to preserve or improve the current recent-history limit.

29. **P1 — §13; `friendships`: directed friendship contradicts the public API.** Although `Player` stores a local set, adding and removing a friend currently updates both players (`src/Quesshi.Server/Api/GameEndpoints.cs:111`, `:117`). The target’s explicitly directed relation silently changes friend lists, invitations and the friends leaderboard for the other person. **Fix:** preserve mutual insert/delete operations atomically under ordered player locks, or identify directed following as a deliberate product change.

30. **P1 — §13; `leaderboard_scores`: accumulated penalties change the zero-floor behaviour.** Today each abandonment applies `max(current total − penalty, 0)`; an unpaid penalty does not consume future earnings (`src/Quesshi.Domain/Player.cs`, `RecordAbandonment`). In the target, a player with zero points and a 200-point penalty remains at zero after earning another 100 points because penalties accumulate separately. **Fix:** explicitly decide whether penalties create debt; to preserve today’s rule while processing events out of order, recompute the chronological earned/penalty ledger with a floor at each event rather than subtracting lifetime totals.

31. **P1 — §§13, 19.1; `player_stats`: per-player category accuracy has no defined replacement.** Today `PlayerGrain.SettleMatchAsync` records each player’s category answers (`src/Quesshi.Grains/PlayerGrain.cs:49`), and profiles read `Player.ByCategory`; the target’s `question_stats` aggregates by question, not player/category. A migrated profile loses its category performance section even though the mapping says those fields move into plugins. **Fix:** define the player/category aggregate or a bounded query over authoritative answers, including misses, forfeited unplayed slots and deleted categories.

32. **P1 — §§12, 19.3; `media_assets`, `questions.media_id`: existing media URLs cannot be imported unchanged.** Today forms and imports accept external or relative URLs, while the target permits only a media-asset reference with stored bytes/hash (`src/Quesshi.Server/Api/QuestionImport.cs:91`; `docs/importing-questions.md`, “Media”). Exporting only question/category JSON leaves uploaded and Wikipedia-sourced files behind, or requires a download/conversion pipeline not in the cut-over. **Fix:** specify URL-to-asset conversion and media export/copy, retain attribution, and make the bank import verify every referenced asset before release.

33. **P1 — §§11.1–11.2, 15, 19.1; `admins`: retained admin-account functions are unsupported by the schema.** Existing admins can be activated/deactivated, have a unique reset email, show last-login information and cannot delete the last administrator (`src/Quesshi.Server/Api/AdminAccountEndpoints.cs:24`, `:36`, `:53`). The schema lacks active state and last-login data and makes email non-unique, so disabling an admin cannot persist and email-based reset lookup becomes ambiguous. **Fix:** add the required fields/uniqueness and define self-disable, final-owner removal, tenant-membership changes and session revocation for global admins.

34. **P1 — §§5.2, 10.3, 17: disabling a kind or format can strand an active session.** The client removes disabled plugins immediately, but running sessions must retain their drawn kind’s play components and grading for up to 90 days. Turning off `map_pick` while its question is open can therefore remove the only playable component while the session continues. **Fix:** separate “available for new creation/draw” from “needed to play or read existing sessions”; continue serving existing sessions and their required components, with a separate explicit cancellation operation.

35. **P1 — §§5.2, 16: the static client registry conflicts with lazy assembly loading.** An eagerly constructed registry using `typeof(MapPlay)` or admin component types from a lazy assembly needs those types before that assembly has loaded, producing a startup/load failure or forcing eager loading. Admin components also need their own assembly split; one `Web.Plugins` assembly cannot be partly lazy. **Fix:** keep lightweight descriptors in the eager registry, await `LazyAssemblyLoader` before resolving component types, and name the admin/map assemblies and their lazy dependencies. [Blazor lazy-loading documentation](https://learn.microsoft.com/en-us/aspnet/core/blazor/webassembly-lazy-load-assemblies?view=aspnetcore-10.0).

36. **P1 — §§16, 19.1: the retained PWA worker defeats first-load lazy loading.** `src/Quesshi.Web/wwwroot/service-worker.published.js:14` includes all assemblies and SVGs, and line 37 fetches them concurrently during installation. Even if runtime loading is lazy, admin assemblies and the map still compete for mobile bandwidth during the four-second playable-app window. **Fix:** exclude deferred assemblies and map assets from initial precaching and cache them on demand; measure first load with the service worker actually enabled.

37. **P1 — §16: a per-request `index.html` conflicts with the retained integrity-checked shell cache.** The worker fetches manifest assets using build-time integrity hashes (`src/Quesshi.Web/wwwroot/service-worker.published.js:40`), while the proposed server rewrites the shell per tenant/configuration. A rewritten shell no longer matches its published hash, so shell caching fails and offline fallback becomes unreliable. **Fix:** remove the dynamic shell from integrity precaching and cache a deliberate tenant bootstrap/shell representation, or keep a static shell and fetch tenant bootstrap data separately.

38. **P1 — §17; schema “Orleans”: published membership scripts do not create the promised schema by themselves.** The provider scripts create unqualified `OrleansQuery`, membership tables and functions; simply running them and granting access to `orleans` can install objects in `public`, while runtime queries cannot find them in the intended schema. **Fix:** explicitly create the schema, run the pinned provider scripts with the correct search path, and configure the membership connections/functions to resolve that schema; verify silo startup using only `quesshi_system`. The inspected upstream scripts are [Main](https://raw.githubusercontent.com/dotnet/orleans/main/src/AdoNet/Shared/PostgreSQL-Main.sql) and [Clustering](https://raw.githubusercontent.com/dotnet/orleans/main/src/AdoNet/Orleans.Clustering.AdoNet/PostgreSQL-Clustering.sql); the exact 10.2 package scripts still need verification.

39. **P2 — §§7.4–7.5: specify the actual Orleans timer and deactivation APIs.** A failed turn must request deactivation and finish; awaiting deactivation of itself is the wrong lifecycle model, and enabling timer interleaving would invalidate the working-copy assumptions across database awaits. **Fix:** require `RegisterGrainTimer` with `Interleave=false`, dispose/rearm its one-shot handle explicitly, and use `DeactivateOnIdle()` followed by return/throw without further state use; queued requests then move to another activation. [Timer documentation](https://learn.microsoft.com/en-us/dotnet/orleans/grains/timers-and-reminders), [activation collection](https://learn.microsoft.com/en-us/dotnet/orleans/host/configuration-guide/activation-collection).

40. **P2 — §7.5: long-lived sessions need an explicit idle-collection and retry-timer policy.** A timer does not make a 48-hour or 30-day activation durable, and pinning such activations would retain unnecessary seats/items in memory; after a fault, arming only the already-past `due_at` can repeatedly wake a backing-off grain. **Fix:** allow normal collection for long deadlines, reload/rearm on activation, and schedule the next wake at `retry_at` when backing off; keep short live phases active only as an optimization. The database sweep supplies durability, so final-session reminders and grain storage are unnecessary.

41. **P2 — §§7.5, 17: “picked up within a second or two” is not a silo-failure guarantee.** A sweep can discover the deadline immediately while Orleans still routes to a dead activation until failure detection/directory recovery completes; a partition can similarly delay calls beyond the 10-second outage threshold. **Fix:** make that statement a measured expectation, specify membership/request-timeout settings and distinguish process restart, silo failure and partition tests; define the intended cancellation outcome when recovery exceeds the threshold.

42. **P2 — §§7.5, 8.2: delayed transitions need a specified time anchor.** A countdown timeout handled nine seconds late can open a question using either the old boundary or current decision time; the former gives players a shortened question, and replaying several boundaries can record misses before anyone received a card. **Fix:** state which transitions use scheduled time versus actual opening time, how reveal duration interacts with grace, and how several overdue boundaries are handled below the outage cutoff.

43. **P2 — §§7.4, 9.2–9.3: command views and database views need the same rendering contract.** “Reads never touch grains” is consistent with a command-response exception, but only if the grain’s view uses the same authorization, reveal filtering and format readers as the database renderer. A command response at version N can race with a stream render at N+1, and equal session versions can carry newer effects/configuration. **Fix:** define one renderer over equivalent viewing data and compare session, inbox, effects and configuration versions independently; never let a stale command response overwrite a newer stream view.

44. **P2 — §§3, 10.2: Dapper mappings and tenant transactions need concrete conventions.** Passing a serialized payload as an ordinary string does not automatically make its parameter `jsonb`; array list expansion, record constructor names and UUID conversion can likewise break otherwise valid SQL. **Fix:** define explicit JSON casts or typed parameters, GUID-based IDs, array/`ANY` usage, column aliases and JSON deserialization; require every command in the callback to use the same connection and transaction, with `set_config(..., true)` after `BEGIN`. Composite foreign keys need consistent SQL predicates, not PostgreSQL composite-type mapping. [Npgsql JSON mapping](https://www.npgsql.org/doc/types/json.html).

45. **P2 — §§7.4, 9.3, 17: pool sizing does not account for the combined workload.** Two data sources mean separate pools; grains, repeatable-read view rendering, presence updates, reconciliation and jobs compete for app connections, while identity, sweeps and membership need system connections. Pool waits alone can consume the answer budget, and adding silos multiplies database connections. **Fix:** specify per-silo connection budgets against PostgreSQL’s total, bounded render/job concurrency and reserved system headroom; release read transactions before awaiting stream writes. Npgsql’s documented default maximum pool size is 100. [Connection parameters](https://www.npgsql.org/doc/connection-string-parameters).

46. **P2 — §9.3: a dedicated LISTEN connection needs a complete receive/reconnect lifecycle.** Registering an Npgsql notification handler alone does not continuously receive notifications on an otherwise idle connection; reconnecting also loses its `LISTEN` registrations. **Fix:** specify an asynchronous wait loop on a non-transactional dedicated connection, reissue `LISTEN` after reconnect, and perform the immediate reconcile only after listening is established; reserve that connection in the pool budget. [Npgsql notification handling](https://www.npgsql.org/doc/wait.html).

47. **P2 — §§9.1, 9.7–9.8: the Blazor streaming request needs more than the browser streaming switch.** Default `HttpClient` completion can still wait for the entire never-ending response, a normal client timeout can kill healthy streams, and treating 401 or `client_outdated` like a transient disconnect creates an endless reconnect loop. **Fix:** specify `ResponseHeadersRead`, asynchronous `SseParser` consumption, same-origin credentials, a lifetime cancellation token, suitable timeout handling, response/content-type validation and terminal versus retryable statuses; cancel the old reader before reconnect or session switching. .NET 10 supports browser response streaming and the framework SSE parser. [Streaming change](https://learn.microsoft.com/en-us/dotnet/core/compatibility/networking/10.0/default-http-streaming), [SSE parser](https://learn.microsoft.com/en-us/dotnet/api/system.net.serversentevents.sseparser-1?view=net-10.0).

48. **P2 — §§9.3, 16: the 30-second slow-client rule cannot mean browser consumption.** A server write may complete into Kestrel/proxy buffers while the browser stops consuming, and a blocked write prevents the same loop from checking its elapsed time. A size-one application channel alone does not enforce the promised disconnect. **Fix:** define the rule as a bounded write/flush deadline, enforce it with an independent cancellation/abort path, disable applicable compression/proxy buffering and cap individual frame sizes; verify the real proxy path.

49. **P2 — §§7.3, 13; `matchmaking_entries` primary key: exclusivity and queue scope are not fully defined.** One queue grain exists per tenant/format, but the table allows only one entry per tenant/player; simultaneous async/live enqueue operations therefore contend across independent writers. It is also unspecified which existing formats hold exclusive seats and whether merely waiting in a lobby or queue reserves one. **Fix:** choose one explicit queue-membership scope, make the key and writer match it, and list exclusivity acquisition/release rules per format, including lobby, elimination, leave, cancellation and failed pairing.

50. **P2 — §13: matchmaking changes today’s matching and offline rules.** Current live pairing matches language/question count and uses the first waiter’s categories/levels (`src/Quesshi.Grains/LiveMatchmakingGrain.cs:74`); current async matching persists a waiting challenge without requiring an open presence stream (`MatchmakingGrain.cs:19`). Requiring full-settings equality and online status for both formats can leave formerly compatible players unmatched or delete legitimate async waits. **Fix:** specify each format’s match key, settings precedence, automatic start, cancellation and presence requirements; identify any intentional changes explicitly.

51. **P2 — §§6.6, 19.1: choice and order authoring bounds are changed or missing.** Today both use exactly four distinct items (`src/Quesshi.Domain/Question.cs:212`); the target permits 2–8 choice options and gives no order-item bound despite retaining a 20-second clock. Also, `SortOrder.Shuffle` applied directly to correct-order input does not satisfy the new answer-independent-card test. **Fix:** preserve four-item bounds for the initial migrated kinds and specify canonical, answer-independent display ordering and opaque option IDs; describe `SortOrder` as adapted rather than unchanged.

52. **P2 — §§7.2, 19.1: the precise bank draw rules need preservation fixtures.** “Rotate categories and ramp difficulty” covers the main rule, but the existing builder also prevents repeated questions, sorts/deduplicates allowed levels, falls back within the selected category scope and then across allowed levels (`src/Quesshi.Application/UseCases/QuestionSetBuilder.cs:13`). Omitting those fallbacks makes previously playable thin banks fail starts. **Fix:** retain those behaviours explicitly and test the actual `LevelForSlot` rounding sequence rather than copying README’s simplified description of equal-sized difficulty bands.

53. **P2 — §§6.2, 13, 19.1: generation settings and post-checks are not mapped precisely.** Today trivia targets are 25/6/6, approved *plus pending* inventory counts, nightly generation defaults off, trivia auto-approval defaults on, and voting generation is separately requested and defaults pending (`TopUpOptions.cs:26`, `:36`, `:44`, `:71`). Generated city verification also needs a country value that is discarded before constructing the stored city payload (`TopUpQuestionBank.cs:316`), so exporting only that payload’s schema cannot reproduce the existing generation check. **Fix:** define per-kind targets, inventory/default/schedule/batch rules and a generation-candidate schema separate from stored payload where necessary; preserve voting’s answer-source selection and illustrated generation.

54. **P2 — §§4, 5.3, 6.2, 8.1: runtime dispatch and wire serialization remain undefined.** `IKind` exposes metadata only, so an engine holding `IKind` cannot invoke the generic kind operations shown; a `Type` settings/action record also does not itself provide validation or preserve JSON metadata under trimming. Orleans additionally requires a concrete serializable grain boundary, not just the HTTP `Command` record. **Fix:** specify the erased adapter used by the engine, version-indexed grading dispatch, validators and `JsonTypeInfo` registration, and the Orleans command/response contracts with stable serializer field IDs; validate a trimmed published client using those actual contracts.

55. **P2 — §§4, 18: namespace architecture tests cannot enforce all claimed dependency rules.** Features sharing one assembly with Application-visible public APIs can access more than the intended plugin API, while purity can be bypassed through helper calls or reflection; project references alone do not separate plugin folders. **Fix:** make core internals inaccessible, place shared contract types where the stated references actually permit them, and define tests over symbol/IL dependencies and forbidden calls; describe dynamic/reflection limits honestly rather than claiming complete enforcement.

56. **P2 — §§15–16, 19.1: the retained admin panel needs an operation-by-operation mapping.** The API inventory does not map active-session monitoring/termination, capacity controls, family category allowlists, thin-bucket dashboard, targeted and illustrated generation, generation/spend history, report dismissal and import dry runs (`src/Quesshi.Server/Api/AdminEndpoints.cs:36`, `:66`, `:97`, `:292`, `:342`).
