3. **P1 — §13: async pairing lacks a complete recovery and ownership protocol.** Step 2 only seats the joiner, although today random pairing also starts the challenge; moreover, an unconditional step-3 delete can remove a replacement entry after the original lease expires, and a lost response after a successful join is reported as failure despite the committed seat ([GameEndpoints.cs:178](/mnt/c/Users/mogha/codes/quesshi/src/Quesshi.Server/Api/GameEndpoints.cs:178)). **Fix:** make the grain operation idempotently join **and start** the waiting challenge, with a stable pairing identity; condition cleanup on the exact session and lease token, and recover an unknown result by checking that joiner’s committed membership before retrying or offering another pairing.

4. **P1 — §7.3: caller-supplied creation IDs need an authorization boundary on replay.** “Finds the row already there and returns it” permits a caller to submit another player’s known session ID as a creation request and receive that row through a path intended for their own newly created session. Reusing an ID with different creation parameters also silently returns an unrelated result. **Fix:** bind creation idempotency to tenant, authenticated creator and a normalized request fingerprint; return the existing creation only when all match, otherwise refuse the collision without returning its data.

5. **P1 — §13; `leaderboard_entries`, `leaderboard_scores`: ledger ordering is incomplete.** Points and penalties from one session have the same `(at, session_id)`, so the stated ordering does not decide which is folded first: from zero, 100 points followed by a 200 penalty yields zero, while the reverse yields 100. Today settlement records the result before applying its penalty ([PlayerGrain.cs:49](/mnt/c/Users/mogha/codes/quesshi/src/Quesshi.Grains/PlayerGrain.cs:49)). **Fix:** define each session as an ordered group—points first, penalty second—and apply/refold the entire group before advancing `last_at` and `last_session`; explicitly include that order in the folding query.

6. **P1 — §§5.6, 14: retiring a feature removes handlers before its queued work drains.** The first retirement release “handles no events,” but previously queued event jobs must complete and the second release waits for an empty queue; removing their dispatch registrations makes those jobs fail rather than drain. **Fix:** retirement stops new event subscriptions, routes and schedules while retaining dispatch handlers for existing jobs, their readers and cleanup; remove those only after the queue has drained.

7. **P1 — §§7.3, 9.5; `session_invites`: invitation expiry is still missing.** Today a live invitation expires with its lobby, while a poll invitation expires ten minutes after being sent; the new invitation table has no expiry and a poll lobby can remain open, leaving an old offer actionable indefinitely ([LiveMatchmakingGrain.cs:141](/mnt/c/Users/mogha/codes/quesshi/src/Quesshi.Grains/LiveMatchmakingGrain.cs:141), [:163](/mnt/c/Users/mogha/codes/quesshi/src/Quesshi.Grains/LiveMatchmakingGrain.cs:163)). **Fix:** store an explicit `expires_at`, preserve those format-specific anchors, filter expired offers from the inbox and enforce expiry when accepting; retain an explicit decline operation as well.

8. **P1 — §13’s use of today’s `LiveRules.AbandonmentPenalty`; §19.1 “kept.”** The existing helper shifts before applying the cap, so sufficiently many abandonments overflow or wrap instead of remaining at 1000—for example, occurrence 66 shifts by 64 and returns 200 again ([LiveRules.cs:38](/mnt/c/Users/mogha/codes/quesshi/src/Quesshi.Domain/LiveRules.cs:38)). The new historical recomputation will repeatedly invoke this helper over an unbounded ledger. **Fix:** preserve the intended rule with explicit tiers `0, 200, 400, 800, 1000 thereafter`, or cap the occurrence before shifting; carry a regression case for large counts into the copied tests.

9. **P2 — §§7.4, 8.1–8.2, 9.4: poll revision handling is specified inconsistently at its boundaries.** The HTTP shape in §9.4 still omits `revision`, activation loads only answered flags and revisions, and generic idempotency still says an existing answer immediately returns the view; those instructions cannot establish equal-revision/different-answer conflicts or permit replacements without an additional path. **Fix:** include revision in the HTTP DTO and cache the normalized answer or a canonical comparison hash; explicitly route poll answers through revision comparison before the generic duplicate shortcut, including a defined response for lower revisions.

10. **P2 — §§5.5, 7.4, 9.3: effects timestamps do not establish causal ordering.** “Database time it was read at” does not identify when the report’s snapshot was established: an older snapshot stamped later can overwrite a newer `done` or rerun status, and a database clock adjustment can also reverse timestamps. **Fix:** give the core effects projection a persisted monotonic revision covering pending, dead, rerun and completed transitions, and read status plus revision together; use that revision for client ordering rather than wall-clock time.

11. **P2 — §7.5: retry wake time and timeout identity are conflated.** A fault leaves `due_at` unchanged but arms the timer for `retry_at`; the internal timeout is then described as identified by the deadline it was armed for and accepted only if that equals `due_at`. Passing the retry timestamp makes that timer a permanent no-op. **Fix:** define separate `wake_at` and `expected_due_at`: schedule at `max(due_at, retry_at)`, carry the original `due_at`, and check both deadline identity and backoff eligibility when the timer fires.

12. **P2 — §8.2; §7.3 started creation: flashcards have no initial 30-day idle deadline.** Only a rating sets the 30-day deadline, so a newly created deck that is never rated has no specified format deadline and falls back to the core’s 90-day limit. **Fix:** initialize the idle deadline during `Start`, then state precisely which actions renew it; make expiry of an entirely unrated deck explicit.
